# Gifvtme — Roadmap & Build Status

This file should be updated frequently — at minimum every time a feature moves from "not started" to "in progress" to "done." Agents should check here before assuming something is or isn't built yet.

## Build sequence (4-month plan, see `architecture/ARCHITECTURE.md`)

**Month 1 — Foundation.** Supabase schema, Sanity schema, auth, manual-entry wishlist creation.
**Month 2 — Core gifting loop.** Scraping, occasion wishlists, sharing, affiliate purchase marking.
**Month 3 — E-commerce & engagement.** Catalog browsing, cart, Flutterwave checkout, order tracking, flash sales, reminders, thank-you messages.
**Month 4 — Reviews, polish, launch.** Reviews, group gifting data model only, responsive polish, bug fixing, soft launch.

- Checkout order-creation race fixed (2026-08-06, follow-up to the pass above) — a code review of the new idempotency logic found `POST /api/checkout` still had a real concurrency bug: it inserted `orders` and `order_items` as two separate statements, so a concurrent request carrying the same `Idempotency-Key` could find the just-committed `orders` row (visible to other transactions immediately) and initiate Flutterwave payment against it before `order_items` existed — worse, if the first request's `order_items` insert then failed, its compensating delete could remove the order the second request had just started paying against. Fixed by moving both inserts into one Postgres transaction via a new RPC, `gifvtme_create_checkout_order` (migration 018, same transactional-RPC pattern as `gifvtme_create_occasion_with_wishlist`) — `POST /api/checkout` now calls this once instead of two sequential inserts, so no request can ever observe an incomplete order. Added two regression tests in `app/api/checkout/route.test.ts` asserting order_items are submitted in the same call as the order and that a losing concurrent request pays against the re-fetched, fully-committed order rather than its own failed attempt. `15-CART-CHECKOUT.md`, `API_ROUTES.md`, `DATABASE_SCHEMA.md` updated. `tsc`, `eslint`, and `npm test` (110/110, up from 108) all clean.
- Checkout idempotency-key signature widened to shipping (2026-08-06, second follow-up to the `15-CART-CHECKOUT.md` pass) — a further code review of the idempotency logic found `getCartSignature` in `CheckoutForm.tsx` only hashed cart contents and `wishlist_item_id`. Since `/api/checkout`'s replay path pays for an order using its originally-stored shipping details (it never re-reads a resubmitted body's shipping), a user who submitted checkout, didn't finish paying, went back to fix a typo'd phone number or address, and resubmitted without touching the cart would keep the same idempotency key — silently shipping the *old*, wrong shipping details. Renamed to `getCheckoutSignature` and folded in every Zod-normalized shipping field (name, email, phone, address, city, state, postal code, delivery instructions), so a shipping correction now mints a fresh key (new order) while an identical resubmission still correctly reuses one. A related suggestion to also include `preferred_payment` in the signature was evaluated and rejected — `preferred_payment` isn't stored on the order at all, `/api/checkout` always forwards the *current* request's value into Flutterwave initiation on every call (fresh or replayed), so it can never go stale; adding it to the signature would instead cause a spurious duplicate order any time someone toggled payment method between submissions. `API_ROUTES.md` and `15-CART-CHECKOUT.md` updated to document the exact signature inputs and the `preferred_payment` exclusion. `tsc`, `eslint`, and `npm test` (111/111) all clean — no new automated test added, since this repo has no component-level test harness for `CheckoutForm.tsx` yet.
- Checkout payment-initiation race fixed (2026-08-06, third follow-up to the `15-CART-CHECKOUT.md` pass) — a further code review found that, even with the order-creation race and idempotency-key fixes above, nothing stopped two concurrent calls into `reinitiateOrderPayment` (`lib/checkout/reinitiatePayment.ts`, shared by `/api/checkout`'s replay path and `/api/checkout/retry`) — a double-click on "Try again," or two idempotency-key replays racing — from each starting an independent, separately-payable Flutterwave session for the same order. The DB would still only ever mark the order `confirmed` once (the webhook's own idempotency guard), but a buyer who completed *both* payment sessions would actually be charged twice by Flutterwave. Fixed with the same `claimed_at` compare-and-set pattern `/api/reminders`/`/api/thank-you/process` already use for cron rows: `orders.payment_claimed_at` (migration 018, set at creation time so even the very first Flutterwave call is claim-protected against a concurrent replay) is atomically claimed — a conditional `UPDATE ... WHERE status IN (...) AND (payment_claimed_at IS NULL OR stale)`, checked for an affected row — before every re-initiation attempt; a losing claim returns 409 without touching Flutterwave, and the claim is released whenever a Flutterwave call fails so a genuine follow-up retry isn't blocked. Stale window is 2 minutes (vs. the cron jobs' 10), since this guards an interactive click, not a background job. Added a regression test asserting a lost claim returns 409 without calling Flutterwave; updated the existing idempotency-replay and race tests for the extra claim-step DB call. `API_ROUTES.md`, `DATABASE_SCHEMA.md`, `15-CART-CHECKOUT.md` updated. `tsc`, `eslint`, and `npm test` (112/112, up from 111) all clean.
