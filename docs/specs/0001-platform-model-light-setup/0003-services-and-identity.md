# Services and identity contract

## Summary

Reuse the existing stack and keep policy in domain services, not page components. API paths and numerical limits below are proposed engineering defaults for this spec review. Phone delivery remains a replaceable integration, and live reminder delivery remains feature 4's responsibility.

## Service boundaries

| Boundary | Responsibility | Reuse and alternative considered |
| --- | --- | --- |
| `lib/contacts/` | Owner scoped person records, explicit linking evidence, import normalization | Follow existing `types.ts`, `validation.ts`, `server.ts` pattern; avoid a separate contacts service |
| `lib/occasion/` | Canonical date resolver, taxonomy, effective occurrence and duplicate identity | Extend current domain, replacing destructive recurrence arithmetic; avoid UI/job specific date rules |
| `lib/important-dates/` | Compatibility adapter and personal date save entry | Keep legacy callers working while delegating to canonical domain; avoid a route/table rewrite |
| `lib/recommendations/` | Replaceable ranker over authorized wishlist data and Sanity curation | Deterministic curated implementation initially; AI engine is unnecessary |
| `lib/auth/phone/` | Challenge request, verify, add/remove method, eligibility, normalized errors | Existing auth provider remains session authority; new SMS adapter/configuration selected during implementation, not a custom identity system |
| `lib/reminders/` | Preference resolution and schedule invalidation contract | Reuse domain location; existing email worker is not evidence of compliant multi channel delivery |

### Draft and save continuation

R-4 replaces the proposed single cookie payload with authoritative temporary journey state. Use a secure HttpOnly first party cookie containing only a cryptographically random browser journey secret; store its hash and the minimal draft in a private temporary database schema. The secret is a bearer capability for this browser's drafts, never a login or a saved User. Draft state has a fixed maximum lifetime of 24 hours from creation, enforced on every read/write plus scheduled cleanup. It creates no auth user, Contact, Occasion, or reminder before authentication. The stored payload is encrypted; no raw draft is logged or projected through the Data API. Use SameSite Lax for top level auth return and private/no-store responses. Do not reuse auth cookies/secrets.

Each draft has a random ID, monotonically increasing revision, created/expiry timestamps, minimal name/relationship/type/recurrence/date input, selected suggestion IDs, current step, and original entry context. Keep the proposed 2 KiB payload bound as a data minimization limit, not a cookie capacity constraint. Exclude product bodies, address books, notes, credentials, addresses, and plaintext share tokens. Shared access survives only through the separate protected reference specified below. Refetch suggestion IDs through the access service before display. Draft edits do not extend expiry.

Every tab holds a draft handle in tab scoped session storage or memory; the cookie identifies the browser session, not a single current draft. New journeys create distinct draft IDs. Updating requires draft ID and expected revision and uses an atomic compare/update. Two editors of the same revision produce one success and one 409 with review/reload or explicit fork options; never last write wins. A duplicated tab with copied handle obeys the same rule. Without a tab handle on reopening, offer a choice among that browser's still accessible drafts rather than replacing one. Forking is an explicit action that creates a new draft ID and no pending save intent.

Save date freezes the current draft revision/digest and issues an immutable server generated `operation_id`, stored with the draft before redirect. Both authenticated manual saves and anonymous save intents use this identity. For an already authenticated explicit Save, bind the operation immediately to the verified server session User and create the durable bound receipt; no new auth attempt is required. Recheck that same User at commit. The client never invents a fresh retry key on refresh. Repeated save-intent requests for the same unchanged draft/revision return the existing noncancelled operation ID; a lost intent response cannot mint a second operation. A failed response is reconciled by reading that operation's owner safe status. Editing a frozen draft cancels the uncommitted intent and requires a new explicit Save action/new operation; it cannot silently change an operation's payload.

For auth continuation, store an `auth_attempt_id`, draft ID/revision/digest, operation ID, journey binding, expiry (15 minute maximum), and pending/verified/consumed/cancelled state. Allow only one outstanding provider authentication attempt per browser journey session because the provider's browser verifier/session cookies are shared. A second tab must wait or explicitly cancel the existing attempt before starting another. It cannot silently overwrite the active binding. Provider OAuth state and code verification remain provider managed; the application records the corresponding provider transaction/challenge reference and validates its own signed attempt cookie on return.

Only the corresponding successful server callback/OTP verification atomically binds the operation to the verified Givtme User and marks it ready. Never infer success from merely finding a current session. `/api/dates/save` requires that exact User, draft revision/digest, operation ID, and live bound continuation for automatic save. It atomically locks/consumes the operation and writes the Contact/Occasion plus result receipt in one transaction. Concurrent consumers receive the committed result, not another write. A business conflict consumes automatic intent into a review state without creating partial records. Retries after commit return the same result, including after a lost response; retries after result deletion return `result_deleted` and do not recreate data.

The durable `save_operations` receipt is created only after authentication and retains the immutable owner binding, draft identity/digest and opaque result IDs; it is not a preauth personal record. A later ordinary visit, expired/cancelled attempt, or an unrelated sign in restores review only. If the current account differs from the bound User, invalidate automatic save and withhold any account bound draft/capability content; offer sign in as the original account or discard/start a new journey. Never rebind an existing operation to another User. Sign out cancels active intents and clears private view state.

On successful save, remove the draft payload and temporary capability material while retaining the minimal owner scoped operation result for retry. Discard removes draft/capability material and cancels intent. Expiry makes data inaccessible immediately and cleanup deletes it; receipts carry no person's input. A 24 hour draft expiry does not erase a committed save result or deletion marker. Browser state alone never authorizes persistence; server validation and duplicate/ownership checks run at commit.

If cookies are unavailable, keep unsent input in page memory and explain that continuation cannot be preserved until storage works; offer retry without claiming success. Invalid or expired journey credentials return an empty recovery state. No personal data or bearer secret is placed in redirects or analytics. All temporary endpoints enforce origin/CSRF checks and journey secret validation before access.

### Shared capability restoration (R-5)

When arriving through a valid shared wishlist link/invitation, the shared access service first verifies the actual capability and scope for the current anonymous/authenticated viewer. Store only the minimum authorization material in an encrypted, private temporary capability record, referenced by a random opaque handle bound to journey session and draft ID. Preserve an existing scoped grant reference when available; otherwise retain the original bearer secret encrypted server side. The draft/browser payload contains only the reference, never the secret, and item IDs/`linked_user_id` are not alternatives to it.

Capability expiry is the earliest of the original grant expiry, draft expiry, and 24 hours; no refresh extends the original grant. At auth return, revalidate the source capability, list visibility/revocation revision, and any invite identity restriction against the verified User before binding that viewer to the reference. Authentication does not claim an unassigned invitation or turn a bearer link into permanent membership. If the source is expired, revoked, private, or identity mismatched, return a safe access unavailable state and generic catalog ideas; keep the person's draft saveable without exposing stale item details.

Every result projection and item action rechecks current source access. Binding is to one verified viewer after auth and cannot be transferred on account switch. Temporary material is deleted on discard/expiry. At successful save, atomically transfer only any still-needed scoped capability to a protected handoff and delete the draft/capability source payload. If a suggestion click follows successful save, hand it back to the existing shared route/access mechanism using a short lived protected handoff reference bounded by both original capability and draft expiry; consume it server side and revalidate before redirect/action. The handoff contains no permanent grant, expires within 15 minutes, and is not written into Contact linkage. Future reminder suggestions use only independently valid existing sharing permissions, never an expired temporary onboarding capability.

### Authentication and phone OTP

Keep `public.users.id` and existing ownership links stable. Use the existing Supabase auth user and its verified identities for multiple methods; do not create a second application User on every provider callback. Session establishment, credential hashing, OTP generation, and verification belong to the auth provider. The SMS vendor is delivery infrastructure, not User identity.

The adapter exposes `requestChallenge(phone, purpose, currentUser?)`, `verifyChallenge(challenge, code, purpose, currentUser?)`, and capability/status checks. Purposes are sign_in and link_phone; link_phone requires an authenticated, recently verified current account. A phone entered in a profile or imported Contact is not a verified sign in identity. Normalize and validate a complete international number; country choice is explicit, not inferred from Contact region.

Recommended initial policy: six digit code, maximum 10 minute expiry, at least 60 seconds between sends to the same phone/purpose, five verify attempts per challenge, five sends per phone per rolling hour, twenty sends per network address per rolling hour, and five link attempts per authenticated account per hour. Apply stricter provider limits when necessary. Responses return server determined expiry/retry timestamps; do not reuse the current email screen's hardcoded 94 second counter. Changing destination invalidates the active challenge. Resend follows the provider's documented challenge lifecycle and must not leave more than one acceptable active challenge for that phone/purpose.

Enforce limits with a shared server/provider store, not per process memory. Store keyed hashes of phone/network keys for rate buckets, expire buckets after their window, and retain no raw OTP. Configure auth provider endpoints/hooks so calling the public provider API directly cannot bypass the effective send budget. Add a server controlled activation switch and provider spend cap; challenge delivery cannot be enabled until these limits, country delivery, and real expiry/replay behavior are verified. A provider that cannot satisfy the verification lifecycle fails the integration gate; do not weaken the UI contract to fit it.

Unconfigured phone capability displays no active send action. Timeouts and provider failures retain the draft, offer retry at the permitted time, and allow existing Google/email methods. Invalid, expired, exhausted, and throttled challenges have stable safe errors. Never log a code or expose whether a random phone belongs to another account. Audit account method changes with actor, method type, result, and opaque provider reference.

Adding Google uses an authenticated linking operation and the provider's verified subject. Adding phone verifies OTP before activation. If an identity belongs to another existing auth account, stop and show a recovery resolution state. Do not silently move owned data or implement an account merge in this feature. Provide return to account settings and existing recovery/support navigation; preserve both accounts while resolution occurs.

Provider native linking to one verified auth user is different from merging two application users. Validate actual Supabase auto linking behavior, User creation hooks, manual linking configuration, and duplicate identity responses in the target project. Never implement application matching by display name or unverified email. If native behavior conflicts with the confirmed no merge policy, block activation and resolve configuration rather than overriding the policy.

Before removing any method, establish that another usable, verified sign in method remains, not merely another profile value. Recheck at mutation time to handle concurrent removals. Do not equate adding a phone sign in method with WhatsApp reminder consent. Existing email login/reset must keep working; the current `/verify-otp` reset flow remains email specific unless safely separated by an explicit purpose.

### Account hub and navigation

`/account` is the authenticated navigation hub. `/account/profile` retains profile editing; `/account/orders` retains the existing order list and `/account/orders/[id]` details; `/account/notifications` owns global reminder settings; `/account/security` owns verified sign in methods. Direct visits authenticate with a safe return to the requested route. Order handlers and data access keep their existing owner checks; displaying a hub creates no new order permissions.

Keep sign out as a user initiated action through the existing auth boundary, available from the hub and optionally other account screens. Do not add a dedicated route. End the session before reporting success, clear session dependent view state and active automatic save continuation, and return to `/`. On failure, retain accurate status and offer retry rather than rendering a false signed out success. Browser back must not restore authorized private data without a current session check.

Do not expose Delete Account in the hub, profile, security, menus, or any destructive account section; do not mount its confirmation dialog or introduce a delete account route. This is removal of the UI affordance for this release, not execution of an account deletion or a new account lifecycle design. Contact/Occasion deletion and sign in method removal remain distinct supported operations with their existing safeguards.

### Recommendations and content

`recommend(context, viewerAccess)` accepts a target requested count of 3 for Dates or 6 for cold discovery, relationship, explicit occasion type, optional Contact ID for authenticated owner requests, and optional protected shared capability reference. It returns `requested_count`, `returned_count`, distinct candidates, rank tier, source type, availability assessment, display projection, permitted action, and source revision. Owner and access rights come from the server, not request flags. No anonymous Contact lookup exists.

R-8 makes counts targets, not guaranteed minimums. Apply the complete approved fallback hierarchy and return at most the requested count. If valid suitable candidates remain fewer, return the truthful smaller count, including zero, with `sparse` or `empty` state. Do not repeat products, invent evidence/availability, weaken condolence suitability, or include unavailable stock just to reach a number. Keep Save date, edit context and Explore more gifts available in every result state, including source errors. The same semantics apply before and after authentication.

Order candidates: accessible intended recipient wishlist, relationship plus occasion, relationship, occasion, broad suitable Museum curation. Deduplicate catalog IDs and repeated wishlist items. Sanity's active content, variant availability, existing catalog normalization, and explicit curation fields supply candidates. An active product with no selectable available variant is excluded. Recheck at action time; a recommendation is not a price or delivery guarantee. Catalog prices retain `formatPrice()` and authoritative checkout validation.

Extend existing Sanity collections with explicit relationship keys, feeling keys, occasion references, and editorial ordering. Preserve collection IDs and current product references. Do not claim relationship suitability from a product title substring or use featured status as proof of popularity. Relationship choices use a shared vocabulary proposed for review: mother, father, partner, sibling, child, grandparent, friend, colleague, mentor, and other with an optional label. Unknown imported/migrated relationship skips that ranking tier without blocking discovery. Do not infer gender, religion, or recipient location from names.

Wishlist projection must enforce visibility, invite/link possession, hidden prices, claim surprise, and revocation before returning data. Linking a Contact is not possession of a share capability. Public lists may be discovered only under feature 3's approved discoverability policy; until that policy exists, use explicit authorized shared context. Cache catalog context independently; never place viewer specific wishlist projections in a shared cache. Catalog responses can use the existing short content revalidation; personalized responses are private and rechecked.

External wishlist items remain visible through the appropriate authorized wishlist context, with an external action and merchant availability unverified. They are not counted as verified purchasable catalog fallbacks. Keep original URL/domain and stored metadata; route via the existing affiliate path where available, otherwise the original validated web URL. This feature does not fetch merchants or alter claims. Foreign/unknown currency metadata is preserved; suppress a numeric Naira price rather than relabeling it. A separate original currency text label may explain source context without changing the global money formatter or adding conversion. Feature 5 supplies normalized currency context before such display is enabled.

Demand/popularity evidence is optional data, not mandatory invented copy. Until feature 8 and feature 3 provide an approved privacy safe aggregate with period, cohort, count, and release rule, omit the evidence slot. In particular, do not query private wishlist contents to manufacture counts. Condolence filters override broad celebratory fallbacks. A source outage returns a recoverable empty/error status without preventing the date save.

### Device and CSV import

Entry requires authenticated ownership and the server managed `user_private_settings.first_manual_date_saved_at`. For migrated users, set that marker only from reliable manual save evidence; otherwise show manual Add a date as the way to unlock import. Removing the first saved date later does not reset successful onboarding.

Device adapter requests selected contacts only, on a deliberate user action, after an explanation of stored fields. Feature detect support and offered fields. No background address book access or permission assumption. Normalize selected names/phone/email only; importing an identifier never verifies it or links an account. Unsupported, cancelled, or denied access returns to CSV/manual choices.

CSV template headers: `name,relationship,phone,email,birthday_day,birthday_month,birthday_year`. Only name/relationship/phone/email can become Contact attributes in this pipeline; date columns are optional candidates for the separate confirmation flow. Empty values mean unknown. A row needs at least one usable explicit name, phone, or email to be a valid person. Missing relationship/date never prevents import. Other personal fields can be edited later; no avatar fetching, formula execution, or inferred data enrichment occurs during import.

Proposed limits: UTF-8 CSV with optional BOM, comma delimiter and standard quoted fields; 1 MiB uploaded bytes; 500 data rows; 100 characters for name, 50 for relationship/custom label, 32 for submitted phone, 254 for email, and a bounded four digit optional year. Reject invalid UTF-8, NUL/binary content, duplicate headers, malformed quoting that prevents reliable row boundaries, unsupported `.vcf`, and excess file/row limits. Extension/MIME alone is insufficient. Unknown headers are shown as ignored, never silently persisted. Treat all values as text and HTML escape output; do not interpret spreadsheet formula prefixes. Any later downloadable error CSV must escape formula capable cells.

Parse and validate the file on the server with resource bounds. Preview returns row IDs, normalized supported fields, per field errors, and date candidate issues. One malformed field invalidates that row for Contact commit when the invalid field would be stored; an invalid optional date candidate can be discarded separately without blocking a valid Contact. Valid rows remain selectable. Explicit review precedes commit; do not select an entire imported address book invisibly.

R-6 uses per row signed integrity evidence rather than a digest of the entire preview. The server issues a batch ID and stable random row ID on initial preview. Each row token signs a versioned canonical payload digest, owner User ID, batch ID, row ID, preview revision, source type, consent policy version, and expiry (30 minutes maximum). The digest includes supported Contact fields, optional date candidates and explicit create/reuse choice plus target Contact ID. Tokens contain no raw personal fields. Every commit validates the current session matches the token owner, signature/expiry, submitted canonical payload, supported schema, onboarding eligibility, and current ownership of any reuse target.

Commit may submit any reviewed subset with each selected row's token; no unselected row is needed to verify it. Preview edits or reuse choice changes require repreview of that row. Return a new token/revision for the same row ID only if it is uncommitted. Use private per row control state containing latest preview revision/digest and expiry, but no raw file or personal payload, so old tokens cannot race a newer edit. Repreview and commit serialize on the same owner/batch/row key. Tokens never substitute for auth or permission.

Per row commit transaction either writes the reviewed Contact/reuse result and immutable committed digest/receipt together, or reports a safe row failure. Successful receipt keys and payloads never change. Exact retry returns the existing result even if the preview token has since expired, after authenticating the owner and matching committed digest; an uncommitted expired token needs repreview. A changed payload for a committed row returns 409 and the owner safe committed result, not a second Contact. Correct a failed row through repreview; previously committed rows remain untouched. If a committed Contact was later deleted, return `result_deleted`, never recreate it from replay.

Retain batch/row receipts for reconciliation, but expire uncommitted preview control metadata after its TTL. Leaving review discards personal preview content; partial results can be reloaded through owner scoped receipts. No automatic merge uses name, phone, or email. Suggest existing Contacts, let the user explicitly choose reuse/new, and never overwrite reused person facts without a separate edit. Any imported birthday still requires its own explicit confirmation and Occasion save operation.

Raw files, unselected contacts, and personal preview payloads stay only in request memory and the current review UI, not database, object storage, logs, or analytics. Leaving/cancelling review discards them. Commit receipts contain operation IDs and outcomes, not original file payload. Confirmed Contacts follow the normal deletion policy. Imported birthdays stay temporary candidates until the owner confirms date/type, then use the standard Occasion save service; no automatic birthday creation on Contact import.

The source adapters output the same normalized row shape. A later vCard adapter can use it without changing review or persistence. No vCard parser or Google Contacts permission is part of this release.

## API surface

Keep handlers thin and reuse `readJson`, Zod schemas, `jsonError`, and server ownership checks. Authenticated APIs return 401 without a session, 404 for missing/nonowned IDs, 409 for conflicts, 422 for valid JSON with invalid fields, and 429 with retry timing for limits. Malformed JSON is 400; safe operational failures are 503. Errors do not expose raw database/provider details. Mutations require same origin/CSRF defenses as well as session checks. All paths below are proposed new routes except the explicitly retained compatibility endpoints.

| --- | --- | --- | --- | --- |

Cursor lists default to 25 with a maximum of 100. Contact detail exposes only the current owner's information. Public draft and suggestion endpoints have bounded payloads and per client abuse controls; suggested initial request ceilings are 60 draft writes and 30 suggestion requests per minute, with debounce to avoid normal typing reaching limits. Production measurement can tune them without changing the journey.

## Configuration and observability

Retain existing Supabase, app URL, Sanity, and email configuration. Proposed new application secrets/settings: `DATES_DRAFT_SECRET` for encrypted temporary journey/capability payloads and domain separated integrity signing (rotatable, server only), `PLATFORM_DATES_ENABLED` for rollout after the blocking prerequisite gate, and `PHONE_AUTH_ENABLED` default false until verification. Private temporary storage and expiry cleanup run in the existing database/service boundary; no new storage vendor is selected. Provider credentials belong in the auth/SMS configuration selected during implementation, never client bundles. Runtime capability detection must agree with deployed configuration. Platform occurrences are controlled configuration with provenance, not hardcoded global Sallah dates.

Use existing analytics transport with content free events: discovery started/results shown, save requested/completed/conflict, draft expired, auth continuation failed, import reviewed/committed/partially failed, and preference changed. Properties may include surface, occasion category, result count/tier, channel, and safe error codes. Do not send names, dates, notes, phones, emails, share URLs/tokens, OTPs, or raw import rows. Avoid sensitive category segmentation such as condolence in externally shared reports without an approved analytics contract.

Record operational counts for pending schedule invalidations, uncertain migrated dates, save failure/retry, import failure, OTP throttling/provider errors, and identity link conflicts. Feature 4 emits sent/failed/skipped/fallback with stage, occurrence key, chosen channel, and safe reason. A timeout is an unknown outcome requiring reconciliation, not evidence that it is safe to send on another channel. No new analytics dashboard or vendor is introduced by this spec.

## Rationale

Existing auth and content providers remain the integration points, while replaceable adapters contain vendor specifics. Explicit sources, limits, and operation keys keep the builder from inventing missing values and prevent successful date saves from being confused with successful delivery. R-1 through R-8 are applied review resolutions. Unchanged numerical limits and endpoint names remain engineering defaults for final spec review.
