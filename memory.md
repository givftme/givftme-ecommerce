- **`components/order/OrderTracking.tsx` bug fixed**: the 4-step tracker rendered `delivered` (the final step) as a perpetually pulsing "in progress" circle instead of a completed checkmark, since the component always treated the current-status step as "in progress" even when it's the last one with nothing left to progress toward.

## Decisions made

- Cancellation is allowed from any non-terminal status (`pending_payment`/`payment_failed` included), not just from `confirmed` onward — explicit developer decision, asked rather than guessed, since this touches a hard business invariant (order lifecycle).
- **`order_status_history`'s legacy `old_status`/`new_status`/`changed_by`/`note` columns were dropped rather than root-caused.** After `status` on already-written rows was observed mutating with no discoverable cause (every mechanism checked and ruled out: app queries, DB triggers, Postgres RULES, generated columns, `pg_cron`, manual SQL — see Problems solved), the developer's call was to stop carrying two overlapping status models rather than keep working around it. This turned out to actually fix the mutation (verified across `under_review → forwarded → shipped → delivered` with zero further drift) — resolved by elimination, exact mechanism never identified.
- `canLeaveReview` means "eligible and hasn't already reviewed," not just "eligible" — the spec's Manual QA section implies the CTA should disappear once reviewed and reappear after delete, which eligibility alone can't produce.
- Two spec-internal contradictions in Reviews were implemented literally rather than silently resolved (same precedent as Order Tracking's transition-map inconsistency): `POST /api/reviews` returns 409 on a concurrent-insert unique-violation exactly as its Backend Logic pseudocode says, even though a separate Edge Case describes that race resolving silently instead.
- No toast-via-redirect convention exists anywhere in this codebase, so one wasn't invented for Reviews' "ineligible direct visit" edge case (renders an inline message instead) — same reasoning as a prior session's search-breadcrumb decision.

## Problems solved

- **`order_status_history` went through three real, live-discovered schema-mismatch bugs before actually working**, none guessed at — each confirmed via direct read-only Supabase access (the service-role key already present in `.env.local`, discovered this session to have REST read access even without a DDL/write path): (1) migration 019 was applied but its `status`/`changed_at` columns were declared only inside a `CREATE TABLE IF NOT EXISTS` block that silently no-opped against an already-existing table with a different shape; (2) even after fixing that, the pre-existing `new_status` column turned out `NOT NULL` with no default and the trigger never supplied it; (3) even after fixing *that*, `status` on already-written rows was observed changing on its own after a later transition, with literally no discoverable write path — resolved not by finding the cause but by removing the legacy columns entirely (see Decisions made). **Technique worth reusing**: `GET {SUPABASE_URL}/rest/v1/` returns PostgREST's own OpenAPI schema — parse it for a table's complete column list, nullability, and defaults in one call, instead of guessing column-by-column.
- Checkout was silently broken (migration 018 partially applied) and, separately, gave zero diagnostic information when Flutterwave rejected a payment — both fixed; the real underlying cause once logging was fixed turned out to be a Cloudflare 403 challenge blocking the developer's local network specifically (a bare curl to the same endpoint from this session's own sandbox got a clean 401), not an application bug. Deliberately deferred rather than chased further: verify once deployed to Vercel (different IP range).
- `information_schema.triggers`, `pg_rules`, `pg_get_functiondef()`, and `information_schema.columns` (`is_generated`) are all queryable directly by the developer via the Supabase SQL editor and were used to exhaustively rule out automated causes for the `status`-mutation mystery — useful diagnostic toolkit if something similar recurs.
